1. Purpose and scope
This specification consolidates the user's explicit architecture corrections, dimensional pages, the four supplied Google Docs, the Blue I Ching reference, the DNA/motif/swarm research links, and the actual Semantic Swarm v2 checkpoint. The next pass must extend the existing Synthia swarm, not invent a replacement swarm, a separate backend, or a parallel architecture. Its first mission is to ingest the supplied classification sources, identify their finite qualities and relationships, resolve positions under user-supplied rules, compose through the existing mesh, and verify every placement against evidence. The long-term mission is executable recursive composition, including the construction of Foundry and further products.
Scope discipline: A specification is not proof of implementation. Source text is evidence and vocabulary, not an automatic mandate to adopt every source's architecture. A user's direct corrections govern interpretation. No source is silently treated as experimentally validated science merely because it supplies a useful computational analogy. The proposed system must remain usable without external LLMs, servers, or web workers wherever the existing browser/no-backend execution requirement applies.
2. Non-negotiable architecture decisions
**ONE accumulating state space.** All imported files, semantic primitives, positional addresses, relations, provenance, histories, capabilities, swarmies, formations, and outputs refer to one logical state space. Distinct tables and views are allowed; separate competing foundational state spaces are not.
**Four originating dimensions:** Movement, Evolution, Being, Design. Their qualities manifest through a macro/micro binary. **Space** is where embodied form is provisionally placed for this implementation, without asserting it must always be the embodiment domain. Some source pages call all five 'dimensions'; preserve that source classification separately from the user's four-plus-Space construction rule.
**Macro/micro binary:** The macro expression remains available in the larger state space; the micro expression becomes an individual, embodied **swarmie**. Both retain a shared origin. The swarmie lives or expresses its quality, encounters other swarmies, affects and is affected by them, and can join larger formations. Original identity and experienced expression are separate fields.
**Four foundational construction processes:** **ATO Engine, Tool Factory, Model Maker (identical to LLM Maker), Neural Encoder.** These are not products created by Foundry. They are the four processes that construct Foundry by composing the finite capabilities already available in the state space. Model Maker and LLM Maker must never be double-counted.
**Five starter components:** the four foundational processes plus **Foundry** as the fifth, emergent constructed component. Foundry subsequently uses the same primitive capability inventory and formed processes to produce pages, programs, tools, apps, models, worlds, and other artifacts.
**Finite capability basis, expansive compositions:** The system does not create capability ex nihilo. Novelty arises from arrangement, binding, parameterization, recombination, feedback, and execution of qualified existing capabilities. Unknown capabilities must be declared unavailable, discovered in existing assets, or added through an explicit reviewed extension.
**Preserve and reuse:** Inspect Drive and GitHub originals, branches, patches, APKs, and zips first; clone before edits; append history; do not delete or gut functionality; do not introduce generic templates or redundant systems; do not bundle unused components.
**Execution must be demonstrated:** A declared formation is not an executable engine. Every runtime claim requires reproducible tests, traces, and actual artifacts. Human Design is a qualitative hypothesis/measurement framework for the labs, not an automatic empirical validation of its claims.

5. Canonical state-space data contract
Use existing tables and interfaces wherever possible. Proposed logical records, not a mandate to replace the existing schema:
`source`: canonical URL/file ID, title, author/date/license where known, file hash, revision, type, extraction method, page/figure/table coordinates, original bytes pointer, confidence and limitations.
`evidence_span`: immutable source location, original wording or data, page/row/figure/cell reference, extraction confidence, and content hash.
`concept`: stable identity, canonical label, aliases, kind, dimensional origin, positional qualifiers, definition, source-specific interpretations.
`relation`: subject, predicate, object, positional context, evidence spans, rule used, epistemic status (`source_explicit`, `derived`, `hypothesis`, `contradicted`, `unresolved`, `tested`), reviewer and history.
`capability`: stable name, input/output contracts, preconditions, side effects, runtime environment, provenance, code location, executable status, tests and version.
`origin`: originating quality and dimension; `manifestation`: paired macro/micro identities and mapping; `swarmie`: micro identity, embodied quality, current state, local interactions, role memberships, capabilities and append-only event stream.
`formation`: composition graph, constituents, assigned roles, motif interfaces, constraints, state transitions, execution bindings, reconstruction recipe and validation results.
`artifact`: Foundry output type, generated bytes/file, build trace, source and capability lineage, reproducibility test, runtime compatibility and delivery location.
`test/observation`: hypothesis, method, controls, variables, qualitative and quantitative measurements, outcome, confidence, limitations, replication and negative results.
Rules: Stable IDs; source revision awareness; no silent overwrite; deduplication by content hash without erasing multiple provenances; typed edges; append-only event records; recoverable histories; explicit unknowns and contradictions. A search hit or co-occurrence is not a validated causal relation.
6. Five cooperating functions of the existing Synthia swarm
6.1 Ingestion
Accept .txt, .md, .docx, text-based .pdf, .json, .csv, .tsv, archives/repositories after safe unpacking, and eventually image/scanned PDFs. Preserve page and table structure, headings, footnotes, figure captions, glyphs, tables, classification rows, and source links. Track OCR/manual-transcription uncertainty where needed. Import incremental revisions without destructive replacement. Large-book ingestion must be resumable, bounded-memory, checkpointed, and auditable. A connector's text extraction is not necessarily the complete 6,000-page source; record actual bytes/pages covered.
6.2 Recognition
Extract candidate finite qualities, aliases, semantic roles, binary pairs, hierarchies, cross-references, positional labels, symbols, tables, and motifs. Distinguish exact terms, synonyms, analogies, homonyms, contradictory definitions, and unrecognized entities. Never silently promote a guessed analogy into a verified mapping.
6.3 Positional resolution
For each candidate answer WHAT, WHERE, WHY, WHO, WHEN where applicable; use address fields and user-supplied traversal, compatibility and perspective rules. Emit a resolution trace: evidence -> parsed claim -> applied rule -> candidate position -> alternatives -> final status. Preserve multiple valid contexts. The resolver should function without relying on an external LLM.
6.4 Composition
Use the existing state-space mesh and capability registry. Build motif connections only where interfaces/constraints permit. Maintain original constituent identities, relationships, and provenance. Swarmies can interact, assume roles, change formations, and affect one another. Distinguish symbolic composition from actual runnable execution. The four construction processes are the basis for assembling Foundry.
6.5 Verification and memory
Check source fidelity, address validity, constraint compatibility, conflicting claims, replayability, artifact execution and experimental results. Append every state transition and correction; do not destroy prior history. Provide human-readable 'why placed here' explanations with source page, exact rule, and confidence. Use an unresolved queue rather than inventing certainty.
7. Macro/micro manifestation and swarmie lifecycle
Identify a qualified originating quality and its four-dimensional association (or explicitly unknown association).
Register its macro expression in the shared state space and a paired micro embodiment; preserve shared origin ID and separate state IDs.
Instantiate a swarmie as a **real runtime instance only when an executable runtime exists**; otherwise mark it `described`/`simulated` rather than `active`.
Expose only capabilities actually registered and supported; provide interaction interfaces and role constraints.
Record encounters, influences, environmental context, changes in expression, and memberships. Do not silently overwrite the originating quality when behavior adapts.
Permit swarmies to combine, split, rejoin, change role, and reconstruct formations while retaining traceable identity and history.
Feed observations back to the same state space with source/experiment tags. Separate subjective semantic quality from measured computational behavior.
Open design question for implementation testing: whether a swarmie's *originating quality* is immutable while its *expressed quality* changes, or whether identity-level transformation is allowed. Do not hardcode the answer without confirmation or a testable rule.

10. The four construction processes and Foundry
ATO Engine: assembly/operation orchestration, scheduling, invocation, transition handling, task graph and executable trace; exact implementation must be recovered from existing assets.
Tool Factory: produces or binds typed tools from existing primitive capabilities, with executable interface contracts and validation.
Model Maker = LLM Maker: assembles or configures language-model-like capability from available components and local model assets, where genuinely supported. It is one process, not two. No outside models should be silently introduced.
Neural Encoder: encodes signals/relations/state into neural representations and transforms where a verified implementation exists; separate the symbolic encoding contract from an actually trained neural network.
Foundry: fifth starter component constructed by the four processes, not their creator. It receives validated formation outputs and makes pages, programs, tools, apps, interfaces, worlds, or other artifacts. It must use original primitives and existing components rather than create parallel ones. Paper/Paper Seed/Paper Loom/Papermate/Notebook Paper/Cardstock, Studio/JavaShoppe, and app DNA are candidate existing Foundry capabilities to inspect and wire, not assumptions that they already work.
Capability proof: Each process must show its code source, input contract, output contract, state-space binding, execution trace and tests. Foundry is working only after a generated artifact is executed/opened and its lineage verified.
